# Architecture Decision Records (ADRs)

Key design choices, hardware trade-offs, and licensing boundaries for *Adapting Open Code LLM Models to Enterprise Warehouses using RAG and LLM Fine-Tuning* (`schema-tuned-sql`).

---

## ADR-001: Model Licensing, Teacher Distillation Terms & Synthetic Customer Scope

### Context
Fine-tuning a small student model on synthetic outputs generated by larger API models requires verifying both the base model's redistribution license and the teacher providers' terms of use, as well as guaranteeing zero leakage of proprietary employer schemas.

### Decision
1. **Student Checkpoints:** Use `Qwen/Qwen2.5-Coder-1.5B-Instruct`, `Qwen/Qwen2.5-Coder-3B-Instruct`, and `Qwen/Qwen2.5-Coder-7B-Instruct`, all released under the **Apache-2.0 License**, which permits commercial fine-tuning, weight merging, and adapter redistribution.
2. **Teacher Models:** Use `deepseek/deepseek-chat` (DeepSeek V3, MIT/permissive model terms) and `qwen/qwen-2.5-coder-32b-instruct` (Apache-2.0) routed through OpenRouter with a hard budget cap (`max_usd: 15.0`). Both model families permit downstream synthetic dataset creation and distillation.
3. **General-SQL Holdout:** Use a self-contained 200-item multi-domain benchmark (`data/general_sql_holdout.jsonl`, modeled on CC-BY-SA 4.0 Spider relational patterns across university, hospital, retail, and aviation domains) executed directly in DuckDB.
4. **Synthetic Warehouse Isolation:** All 11 tables in `warehouse/schema.sql` and all metric formulas in `warehouse/business_definitions.md` are authored from scratch for the fictional company "MetricPulse". Zero real company tables or proprietary employer internals are present.

## ADR-002: Embedded DuckDB Execution & AST Read-Only Guardrail over String Matching

### Context
Text-to-SQL benchmarks often rely on string or exact-match heuristics, which penalize semantically equivalent SQL (e.g., CTE vs subquery, `COUNT(*)` vs `COUNT(1)`, or column alias differences). Conversely, executing untrusted LLM-generated SQL directly in DuckDB introduces security risks because DuckDB supports local filesystem functions (`read_csv('/etc/passwd')`, `read_parquet(...)`, `glob(...)`).

### Decision
1. **Primary Metric:** Score systems by **Execution Accuracy (EX)** in DuckDB (`src/eval/execution.py`) using multiset row comparison (`collections.Counter` of normalized tuples, order-insensitive unless the gold AST contains an explicit `ORDER BY`, with $10^{-4}$ relative float tolerance).
2. **Two-Layer Execution Sandbox (`src/utils/db.py`):**
   - Connection-level lock: `enable_external_access="false"` followed by `SET lock_configuration=true;`.
   - Pre-execution AST inspection via `sqlglot`: `ReadOnlySQLGuardrail` rejects any non-`SELECT`/`UNION` statement, multi-statement strings, schema-qualified system tables, table functions in `FROM`, and prohibited functions (`read_csv`, `read_parquet`, `sniff_csv`, `glob`, `duckdb_settings`).

## ADR-003: NVIDIA Tesla T4 (Turing sm_75) Precision & Numerical Stability

### Context
The target training and serving hardware is the **NVIDIA Tesla T4** (16 GB GDDR6, Turing architecture, compute capability `7.5`). Many modern LLM training recipes default to `bfloat16` and `flash_attention_2`, both of which require Ampere (`sm_80`) or newer GPUs. Furthermore, pure FP16 training on Qwen2.5 checkpoints can suffer gradient underflow or `NaN` loss spikes when adapter weights are updated in FP16.

### Decision
1. **Precision & Attention:** Enforce `precision: fp16` (`torch.float16`) and `attn_implementation: sdpa` (PyTorch native Scaled Dot-Product Attention) via `validate_t4_constraints()` in `src/train/sft.py`.
2. **FP32 Master LoRA Weights:** When initializing PEFT LoRA/QLoRA on T4, upcast all trainable adapter parameters (`requires_grad=True`) to `torch.float32` while keeping frozen base weights in `float16` (1.5B) or 4-bit `nf4` with double quantization and `float16` compute dtype (3B/7B), paired with `paged_adamw_8bit`, gradient checkpointing, and `max_grad_norm: 1.0`.
3. **Completion-Only Loss Masking:** Use `DataCollatorForCompletionOnlyLM` (`mask_completion_only_labels`) so cross-entropy loss is computed strictly on the SQL completion tokens, preventing the 900+ token schema prompt from dominating gradients.

## ADR-004: Execution-Verified Distillation & Contamination Filtering

### Context
Unfiltered teacher SQL outputs include hallucinated column names, dialect mismatches (Postgres/MySQL functions incompatible with DuckDB), and empty result sets that degrade student accuracy if included in SFT.

### Decision
Filter every candidate training pair through `SQLVerifier` (`src/datagen/verifier.py`) and `ContaminationFilter` (`src/datagen/dedupe.py`):
1. Must parse in `sqlglot` (`read="duckdb"`) and pass `ReadOnlySQLGuardrail`.
2. Must execute in DuckDB and return a non-empty, non-null result set on the seeded warehouse (or emit an explicit refusal token on negative queries).
3. Must not match any frozen `test_gold.jsonl` or `dev.jsonl` item by normalized AST or exceed character 3-gram cosine similarity $\ge 0.85$.
